# AI4Materials Knowledge-Graph Projects: Common Points and Differences

<details>
<summary>Common Points</summary>


### Entities

Each project turns materials information into named objects that can be connected and queried. Typical entities include materials, chemical elements, crystal structures, properties, experiments, papers, devices, and processing steps.

Examples:

- **MatKG** identifies materials-science entities in the literature; for example, a paper can yield `LiFePO4`, `olivine structure`, `ionic conductivity`, and `solid-state synthesis` as linked entities.
- **Materials Knowledge Graph via LLM** extracts entities from energy-materials abstracts; for example, an abstract about a perovskite solar cell can yield `MAPbI3`, `band gap`, `power conversion efficiency`, and `spin coating`.
- **Propnet** represents materials, quantities, units, and property models; for example, for a silicon sample it can connect the entities `Silicon`, `Mass(5.0 g)`, `Volume(2.0 cm^3)`, `Density(2.5 g/cm^3)`, `Gram`, `Cubic centimeter`, and the model `density = mass / volume`.
- **Materials Experiment Knowledge Graph** represents samples, instruments, procedures, and experiments; for example, experiment `E-2026-014` can connect sample `S-001`, an `X-ray diffractometer`, an `800 °C annealing` procedure, and a phase-composition measurement.

For example, a sentence such as:

```text
Al-doped ZnO thin films were deposited by sputtering and showed a band gap of 3.31 eV.
```

could be converted into:

```text
(Al-doped ZnO thin film)
	├─ instance_of ─────> Material
	├─ synthesized_by ──> Sputtering
	├─ has_property ────> Band gap
	└─ described_in ────> Paper:10.xxxx/example-doi

(Band gap)
	├─ has_value ───────> 3.31
	└─ has_unit ────────> eV
```

This supports a question such as “Which deposition methods were used for Al-doped ZnO?” without requiring the system to rediscover the relationship from the original paragraph every time.

### Relations

The projects store meaning in links between entities, not only in document text. A relation can describe composition, synthesis, measurement, application, derivation, or citation.

```text
Material ──has_property──> Band gap
Material ──synthesized_by─> Procedure
Experiment ──measures─────> Property
Claim ─────supported_by───> Paper
```

For example, MatKG can connect `LiFePO4` to a synthesis method and an ionic-conductivity measurement from the same paper, while MEKG can connect sample `S-001` to its X-ray diffraction output. Propnet uses relations such as `has_mass`, `has_volume`, `has_property`, and `derived_from` to explain how `Silicon` has `Density(2.5 g/cm^3)`, calculated from `Mass(5.0 g)` and `Volume(2.0 cm^3)`.

A concrete Propnet-style entity graph could be:

```text
Material: Silicon
	├─ has_mass ────────> Quantity: 5.0
	│                      └─ has_unit ─> Unit: g
	├─ has_volume ───────> Quantity: 2.0
	│                      └─ has_unit ─> Unit: cm^3
	└─ has_property ─────> Density: 2.5
	                       ├─ has_unit ─> Unit: g/cm^3
	                       ├─ derived_from ─> Mass: 5.0 g
	                       ├─ derived_from ─> Volume: 2.0 cm^3
	                       └─ generated_by ─> Model: density = mass / volume
```

The same relation pattern can describe an experimental chain:

```text
Sample S-001
	-> prepared_by: ball milling
	-> heat_treated_at: 800 °C for 2 h
	-> characterized_by: X-ray diffraction
	-> produces_measurement: phase composition
```

It can also describe a photovoltaic application:

```text
MAPbI3 ──used_in──────> Perovskite solar cell
MAPbI3 ──has_property─> Band gap: 1.6 eV
```

### Sources

Graph construction usually combines more than one source medium. Here, a source means the place or format that carries the information: a research paper, an abstract, a database record, a dataset, an experiment record, a code library, a written rule, or a model-generated output. Each source contributes different kinds of content and can be linked to the graph facts created from it.

Examples:

- **MatKG** uses research papers and their DOI metadata; for example, a paper reporting Al-doped ZnO deposition can supply the material, sputtering method, band gap, and DOI.
- **MOF-KG** combines MOF database records with research papers. A MOF database is a structured collection of framework records, chemical structures, linkers, metal nodes, and measured properties; for example, a query can join a database record for a water-stable MOF with a paper reporting its `1,245 m^2/g` surface area.
- **NR-KG** uses alloy datasets and prediction code; for example, a dataset record can provide Fe-Co-Ni-Cr composition and a measured `920 MPa` yield strength, while code uses these records to train or evaluate a prediction model.
- **SolarGraph AI** uses RDF/OWL data files and cited photovoltaic facts; for example, one data file can state that a perovskite material is used in a solar-cell device and has a `1.6 eV` band gap, while another field records the supporting source.

The common pattern is:

```text
papers + abstracts + databases + datasets + records + code + rules
												 │
												 ▼
			 extraction / normalization / entity linking
												 │
												 ▼
								 materials knowledge graph
```

For instance, a paper can provide an Al-doped ZnO band-gap claim, a database can provide a structure identifier, a spreadsheet or dataset can provide a measured value, an experiment record can provide the sputtering conditions, and a code library can provide the calculation used to derive a property. Entity linking connects these source records when they refer to the same material.

### Provenance

A useful graph records where a statement came from and how it was produced. This makes it possible to distinguish a reported measurement from a calculated value or a model prediction.

Examples:

- **MatKG** provides source DOIs and public graph data; for example, the Al-doped ZnO band-gap fact can retain the DOI of the paper from which it was extracted.
- **Materials Knowledge Graph via LLM** links extracted information to article provenance; for example, the `MAPbI3` band-gap entity can point back to the abstract and DOI that mention it.
- **MEKG** records the history of materials experiments and workflow steps; for example, the graph can trace the phase-composition measurement for `S-001` back through X-ray diffraction to experiment `E-2026-014`.
- **SolarGraph AI** uses PROV-O and citation-aware retrieval to support traceable answers; for example, an answer about a perovskite solar cell can cite both the device relation and the paper supporting it.

An MEKG-style provenance path could be:

```text
Measurement: phase composition
	<- produced_by: X-ray diffraction
	<- performed_on: Sample S-001
	<- heat_treated_at: 800 °C for 2 h
	<- reported_in: Experiment E-2026-014
```

This lets a researcher answer “Which heat treatment produced the phase composition in experiment E-2026-014?” with a traceable sample and experiment, rather than an unsupported general statement.

### Reasoning

The graph supports more than keyword lookup by following several links or applying a model to structured values.

Examples:

- **Propnet** derives a property from other properties while preserving units; for example, it derives `2.5 g/cm^3` from `5.0 g / 2.0 cm^3`.
- **MOF-KG** evaluates multi-hop question answering, such as finding materials that satisfy several conditions; for example, it can find a MOF with linker `L`, stable-in-water status, and surface area above `1,000 m^2/g`.
- **NR-KG** combines graph structure and numerical features to predict high-entropy-alloy properties; for example, Fe-Co-Ni-Cr composition and neighboring alloy records can support a predicted yield strength of `900 MPa`.

For example, Propnet can represent a density derivation:

```text
mass = 5.0 g
volume = 2.0 cm^3
density = mass / volume = 2.5 g/cm^3

Density(2.5 g/cm^3)
	├─ derived_from ─> Mass(5.0 g)
	├─ derived_from ─> Volume(2.0 cm^3)
	└─ generated_by ─> Density = Mass / Volume
```

The graph preserves the inputs and units, so a later calculation can identify that a mass in `kg` must be converted before it is combined with a volume in `cm^3`.

An MOF-KG query can combine several constraints:

```text
Question: Which MOFs contain linker terephthalate, are stable in water,
		  and have a surface area above 1,000 m^2/g?

MOF
	-> has_linker -> Terephthalate linker
	-> has_property -> Water stability: stable
	-> has_property -> Surface area: 1,245 m^2/g
```

A simplified Cypher-like form is:

```text
MATCH (m:MOF)-[:HAS_LINKER]->(l:Linker),
	  (m)-[:HAS_PROPERTY]->(s:Stability),
	  (m)-[:HAS_PROPERTY]->(a:SurfaceArea)
WHERE l.name = 'terephthalate'
  AND s.value = 'stable'
  AND a.value > 1000
RETURN m.name, a.value
```

For NR-KG, a prediction may use an alloy's composition and neighboring graph records:

```text
Alloy: Fe-Co-Ni-Cr
	├─ contains ─> Fe
	├─ contains ─> Co
	├─ contains ─> Ni
	├─ contains ─> Cr
	└─ has_property ─> yield strength: 920 MPa

composition + neighboring alloys + known properties
						 │
						 ▼
				 graph prediction model
						 │
						 ▼
			 predicted yield strength: 900 MPa
```

The predicted value should remain distinguishable from the measured value, with its model, input records, and uncertainty retained as metadata.

```text
Question
	 │
	 ├─ identify entities and constraints
	 ├─ follow relevant graph relations
	 ├─ apply property/model calculations when needed
	 └─ return values together with supporting evidence
```

### Retrieval

These graphs can provide structured context for GraphRAG systems. Retrieval can resolve an entity, traverse related nodes, and return evidence instead of passing an entire document collection to the language model.

```text
question
	-> entity linking
	-> graph traversal / SPARQL / Cypher
	-> relevant facts and source passages
	-> grounded answer
```

**KGQA4MAT / MOF-KG** focuses on translating natural-language questions into formal graph queries. **SolarGraph AI** demonstrates an end-to-end GraphRAG workflow using RDF, SPARQL, SHACL, and a ReAct-style agent. The same retrieval idea can also make literature-scale graphs such as MatKG more useful for multi-hop scientific questions.

For a question such as “Why is `MAPbI3` relevant to perovskite solar cells?”, a grounded retrieval path could be:

```text
user question
	-> identify MAPbI3
	-> retrieve application and device relations
	-> retrieve supporting paper or dataset
	-> check graph constraints and provenance
	-> generate answer with citations
```

The answer can cite both the graph relations and the source supporting each relation, rather than returning a paragraph based only on semantic similarity.

### Reproducibility

Most projects expose at least part of their implementation, data, schema, or graph export. This allows another researcher to inspect the representation, reproduce a query, or compare a result with its source.

Examples include MatKG’s GitHub code and Zenodo export for inspecting a literature graph, Propnet’s public Python library for rerunning a density calculation, MEKG migration and database tooling for loading `E-2026-014`, NR-KG datasets and PyTorch code for reproducing an alloy prediction, and SolarGraph AI’s RDF/OWL resources for validating a cited photovoltaic answer.

### Detailed Interpretation of the Additional Projects

The additional entries extend the original seven projects along several dimensions.

### Foundational Data Integration

MMKG connects general linked-data sources for metallic materials, while NanoMine and the battery-cathode KG organize domain-specific materials, processes, and properties. These projects emphasize schema alignment and scientific context before question answering.

### Discovery and Assistance

Knowledge Graph-Empowered Materials Discovery and the Compound KG assistant use graph relations to support recommendation or researcher-facing assistance. Their value is in connecting candidate materials to evidence and related concepts, rather than treating discovery as a similarity-only search.

### Terminology and Ontology

The Materials Terminology KG makes concepts extracted from a corpus searchable as a terminology network. The upper-level ontology study addresses a different layer: choosing a formal foundation such as BFO, EMMO, or PROVO for future materials graphs.

### Structured Extraction

The materials-table study, Framework Material KG, LLM-Driven Knowledge Graphs, Materials Literature KG Reconstruction, and the ChemRxiv preprint focus on turning scientific text or tables into entities, relations, values, and provenance. Their main differences are source format, domain scope, and degree of preprocessing.

### Specialized Retrieval

The zeolitic KG, CLASS MATE, Materials Property KG, TopoChat, polymer expert system, heterogeneous materials KG, and OptoMatKG adapt graph retrieval to specific scientific domains or user workflows. They differ in whether the graph primarily supports semantic search, multi-hop QA, property lookup, or traceable evidence retrieval.

### Agentic and RAG Systems

TopoMAS and GraphAgents place a KG inside an iterative materials-design agent, whereas the reified KG and polymer VectorRAG/GraphRAG work focus on evidence representation and retrieval evaluation. These systems make the boundary between graph construction, retrieval, and downstream reasoning explicit.

Together, the additions show that AI4Materials knowledge graphs are not one architecture. They range from linked-data and ontology resources, through extraction pipelines and domain graphs, to provenance-aware retrieval and agentic design systems.

<details>
<summary>Overall Interpretation</summary>


These projects are complementary rather than interchangeable: MatKG and the LLM-based MKG emphasize literature-scale extraction, Propnet emphasizes property reasoning, MEKG emphasizes experimental provenance, MOF-KG emphasizes KGQA evaluation, NR-KG emphasizes numerical prediction, and SolarGraph AI demonstrates an end-to-end GraphRAG interface. A practical AI4Materials system could combine their strengths by linking literature entities to structured databases, property models, experiment provenance, and citation-aware retrieval.
